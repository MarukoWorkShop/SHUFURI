## 一、产品概述

### 1.1 一句话定位

**SHUFURI 是一个用后即走的在线外语歌词排版工具——用户通过外部 AI 获取歌词和语法数据，在 SHUFURI 完成排版、微调、导出和打印。**

### 1.2 核心价值主张

市场上没有任何一个工具能在一个页面内完成"假名注音 + 翻译 + 语法注释 + 精美排版 + 多格式导出"的完整工作流。用户目前需要串联 2-3 个工具手动整理格式，SHUFURI 把这个流程压缩到一个页面。

**关键差异化：SHUFURI 的两层架构。** 歌词生成和翻译由外部消费级 AI（豆包等免费 App）完成，SHUFURI 不内嵌 AI 生成歌词——这让核心排版流程零 AI 成本、永久免费。在此基础上，SHUFURI 提供 AI 驱动的学习增强功能（划词讲解、语法点自动补充），这部分有真实 API 成本，当前采用**内测反馈墙 + 双层每日免费额度**机制（非付费墙），未来演化为正式 freemium。

- **核心工具层（永久免费）**：口令生成 → 外部 AI → 粘贴排版 → 导出打印。没有 AI API 成本，没有服务器算力成本
- **AI 学习增强层（当前内测反馈墙）**：划词 AI 讲解（FEAT-05）+ 内嵌语法/词解生成（FEAT-06）。每日免费额度（划词 20 次 + 词解 5 次），额度耗尽后弹出反馈墙，提交反馈赠送额外划词额度。无支付、无订阅、无账号体系
- **歌词准确性由用户和外部 AI 负责**——SHUFURI 不对歌词内容准确性背书
- **为什么这样分层**：歌词生成是最高频、最重 API 成本的环节，交给免费的外部 AI 完成；SHUFURI 的 AI 成本集中在低频的「讲解/语法补充」上，以**无状态云函数网关**代调大模型（结果只回传当前用户，**不做跨用户内容缓存/分发**），并用个人每日配额 + 反馈墙控制成本与收集偏好数据

### 1.3 产品类型

工具型网站（Tool Site），非内容平台、非社区。核心指标不是停留时长，而是"完成率"——用户能否在 3 分钟内完成一次排版并导出。商业模式分两步走：当前内测期为"核心工具永久免费 + AI 学习增强内测反馈墙"（无支付逻辑），未来演化为正式 freemium（核心工具层永久免费，AI 学习增强层免费有限额 + 高级订阅）。

### 1.4 核心工作流（已确认）

```
用户想标注一首歌
    ↓
SHUFURI 生成「搜索 + 结构化」口令 → 一键复制
    ↓
用户切到外部 AI（豆包等免费 App）→ 粘贴口令
    ↓
外部 AI 返回结构化记录流（歌词 + 假名 + 翻译 + 语法点）
    ↓
用户复制结果 → 回到 SHUFURI → 粘贴并排版
    ↓
SHUFURI 自动解析 → 精美排版（B5 海报 / 手机竖屏）→ 墨微调
    ↓
（可选）AI 自动补充语法解释 → 划词 AI 深度讲解（每日免费额度：划词 20 次 + 词解 5 次）
    ↓
（额度耗尽时）反馈墙 → 提交反馈 → 赠送划词 +50 → 继续使用
    ↓
导出（PDF / PNG / HTML）或打印 → 带走
```

**两条 AI 路径的明确区分：**

| 路径 | 做什么 | 谁做 | 成本 | 状态 |
|------|--------|------|------|------|
| **AI 生成歌词** | 搜索歌词全文 + 假名 + 翻译 | 外部 AI（豆包等免费 App） | 用户端，零 SHUFURI 成本 | ✅ 唯一歌词来源路径 |
| **AI 补充语法解释** | 对已排版歌词生成词解/语法区段 | SHUFURI 内嵌（FEAT-06） | SHUFURI API 成本 | ✅ 活跃，内测反馈墙模式 |
| **AI 划词讲解** | 选中歌词片段 → 深度讲解 | SHUFURI 内嵌（FEAT-05） | SHUFURI API 成本 | ✅ 活跃，内测反馈墙模式 |

### 1.5 商业模式（内测反馈墙 → freemium 演进）

SHUFURI 采用两层定价架构，分三阶段演进：

| 层 | 包含功能 | 当前定价 | 成本结构 |
|----|---------|------|---------|
| **核心工具层** | 口令生成、粘贴排版、墨微调、分页、导出（PDF/PNG/HTML）、歌词本、学习卡、Anki 导出 | **永久免费** | 零 API 成本（歌词由外部 AI 生成，排版导出纯客户端计算） |
| **AI 学习增强层** | 划词 AI 讲解（FEAT-05）、内嵌语法/词解生成（FEAT-06） | **当前：内测反馈墙（无支付）** → 未来：freemium | 火山引擎豆包 API 成本，由个人每日配额约束（**无**跨用户词解内容缓存） |

---

#### 阶段 1 — MVP / 内测期（当前，无支付逻辑）

**核心机制：双层每日免费额度 + 反馈墙激励。** 代码中无任何订阅、价格、支付、解锁高级功能的逻辑——这是刻意设计，不是遗漏。

| 动作 | 每日免费额度 | 提交反馈后 |
|------|-----------|-----------|
| 划词讲解（explain） | 20 次 | +50 → 70 次 |
| 词解与语法生成（lyrics） | 5 次 | 不变（仍 5 次） |

**存储与重置：**
- 额度计数存储在 LocalStorage（key: `shufuri_ai_usage`），按设备/浏览器隔离，前端防君子机制
- 跨过本地 0 点自动清零（`todayKey()` 比对日期）
- 无账号体系——换设备/清浏览器数据即重置

**反馈墙 UI（AiLimitFeedback.tsx）：**
- 触发：任一额度耗尽 → `tryUse()` 返回 false → `createPortal` 弹出反馈墙
- 墙内包含：当前额度提示（区分划词/词解耗尽，说明"搜索与打印排版仍可无限畅享"）、评分滑块（1-100）+ 预设档 60/80/90/100、反馈文本框（最多 500 字，可选）
- 提交反馈后：调 `submitFeedback()` 上报（匿名存 NoSQL）→ 无论服务端成败，本地 `grantFeedbackBonus()` 赠送划词 +50 → 跳转"感谢支持，正式版本正在筹备中"页
- 跳过选项可用

**后端"防小人"限额（云函数侧）：**
- 每 IP 每 3 秒最多 3 次请求
- prompt 长度上限 8000 / 16000 字符
- 前端消费 `RATE_LIMITED` 错误码
- 用量元数据可记入 `ai_usage`（token/action/uid，**不含**歌词正文或生成全文）

**隐私与内容分发（MVP 硬约束）：**
- 用户输入的歌词与 AI 生成的学习材料仅在用户设备保存（用户主动「保存到我的歌词库」或导出时）
- 云端 AI 网关（`arkProxy`）为无状态透传：请求 → 官方 API Key 调大模型 → 结果只回传当前请求方
- **不**把生成内容写入可供其他用户读取的数据库，**不**提供基于内容哈希的跨用户复用（FEAT-16 已退役）

**埋点漏斗（AiLimitContext.tsx）：**
- `trackFirstAiUse`（激活率）、`trackAiLimitHit`（触达率/Hook Rate）、`trackFeedbackShown`（反馈墙曝光）、`trackFeedbackSubmitted/trackFeedbackDismissed`（转化/跳过）
- 用于衡量"反馈墙 → 提交反馈"的转化漏斗

> **方案本质：** 这是一套"内测期用反馈换额度"的增长/调研机制，不是商业化收费墙。用反馈问卷的成本远低于搭建支付系统，同时收集用户偏好数据为未来定价提供依据。

#### 阶段 2 — V2（上线后 1-3 个月）

- 引入用户账号体系（跨设备额度同步，替换 LocalStorage）
- 反馈墙保留但作为可选，不再是唯一"解锁"方式
- 评估是否引入付费层（需看 API 成本曲线和用户反馈数据）

#### 阶段 3 — V3（3-6 个月）

- 正式 freemium：免费层 + 高级订阅
- 基于内测期收集的反馈数据和 API 成本曲线定价
- 核心工具层（排版/导出）永久免费，AI 学习增强层（划词 + 语法）高级收费
- 成本控制依赖配额与订阅，**不**依赖跨用户内容缓存命中

---

**宣传口径：**
- "SHUFURI 核心功能永久免费——歌词排版、导出、打印，零成本"
- "AI 语法讲解功能每日有免费额度，用完提交反馈即可继续使用"
- 不提"永久免费"覆盖 AI 功能——AI 功能有真实 API 成本
- 不提"付费/订阅/会员"——当前无支付逻辑，避免误导用户

### 2.2 市场缺口分析

**缺口 1：无 Web 端歌词专用排版工具**
EZFurigana 是 Web 端但通用文本无排版；FuriganaLyricsDesigner 和 JLTool 是歌词专用但桌面端。没人占据"Web + 歌词专用 + 精美排版 + 导出"这个交叉位置。

**缺口 2：无"外部 AI + 专业排版"的分工模式**
所有工具要么自己做 AI（成本高、需 API Key），要么纯手动（效率低）。SHUFURI 首创"外部免费 AI 生成 + 专业排版工具"的分工——用户用免费的豆包生成内容，用 SHUFURI 排版导出，两边都免费。

**缺口 3：无"用后即走"的轻量体验**
现有工具要么需要安装、要么需要注册、要么是重平台。没有"打开即用、用完导出、不留痕迹"的极简体验。

**缺口 4：无多语种歌词标注**
绝大多数工具仅支持日语。韩语歌词（K-POP/韩剧 OST）、中文歌词（对外汉语学习）、英语歌词同样有标注需求但无专用工具。SHUFURI 已实现 4 语种全覆盖。

### 2.3 SHUFURI 差异化定位

```
           工具属性 ↑
                    │
    SHUFURI ★       │    JLTool
                    │    FuriganaLyricsDesigner
    EZFurigana      │
                    │
  ──────────────────┼──────────────────→ 语言学习属性
                    │
    LrcSong         │    Genius
                    │    Musixmatch
    Lyrical Nonsense│
                    │
           内容属性 ↓
```

SHUFURI 占据**"高工具 + 高语言学习"**的空白象限——比 EZFurigana 更聚焦歌词场景且具备排版导出，比 JLTool 更轻量（Web 免安装），比 Genius 更实用（导出带走 vs 只能在线看），且独创"外部 AI + 专业排版"的免费分工模式。

## 三、目标用户

### 3.1 核心用户画像

#### 画像 A：日语歌词学习者（P0 核心用户）

| 属性 | 描述 |
|------|------|
| **年龄** | 18-30 岁 |
| **身份** | 大学生 / 上班族 / 二次元文化爱好者 |
| **日语水平** | N5-N3（初级到中级），能读平假名但不熟汉字读音 |
| **行为特征** | 听 J-POP / 动漫 OP/ED 时想跟着唱但不会读汉字；用罗马音辅助但觉得"只看罗马音学不到汉字" |
| **核心痛点** | 找到歌词后需要手动查每个汉字的读音，翻译要另开 Google Translate，整理格式耗时 |
| **使用场景** | 听到喜欢的歌 → 用豆包生成标注歌词 → 在 SHUFURI 排版 → 导出/打印 |
| **付费意愿** | 低（学生群体为主），但愿意接受非侵入式广告 |
| **代表搜索词** | "YOASOBI 夜に駆ける 歌词 假名"、"米津玄師 Lemon 振り仮名"、"日语歌词 罗马音 翻译" |

#### 画像 B：韩语歌词学习者（P1 扩展用户）

| 属性 | 描述 |
|------|------|
| **年龄** | 18-35 岁 |
| **身份** | K-POP 粉丝 / 韩剧观众 |
| **韩语水平** | 初级，会 Hangul 字母但不熟词汇 |
| **核心痛点** | 韩语歌词没有类似日语假名的注音系统，需要罗马音标注 + 中文翻译 |
| **使用场景** | 学唱 K-POP 歌曲 / 韩剧 OST → 需要罗马音 + 翻译对照 |

#### 画像 C：外语教学/内容创作者（P2 辅助用户）

| 属性 | 描述 |
|------|------|
| **身份** | 日语教师 / 语言学习博主 / 翻译爱好者 |
| **行为特征** | 需要为教学材料或社交媒体内容制作标注好的歌词 |
| **核心痛点** | 现有工具导出格式不理想，需要大量手动排版 |
| **使用场景** | 制作教学素材 → 导出为图片/HTML/PDF → 分享到小红书/B站/课堂 |

### 3.2 非目标用户（明确排除）

- 需要歌词时间轴同步的用户（用 LrcSong / Musixmatch）
- 需要歌词文化解读的用户（用 Genius）
- 仅需要翻译不需要注音排版的用户（用 Google Translate / DeepL）
- 专业音乐从业者（歌词版权、商业用途）

## 九、SEO 方案

> **JULIA 决策：不做 SSG，零架构改动。首页 index.html 静态文案 + OG 标签即可满足 SEO 需求。**

### 9.1 方案概述

SHUFURI 的 SEO 需求极简：只需首页被搜索引擎收录，让用户搜"日语歌词标注""假名注音工具"等关键词时能找到 SHUFURI。不需要多页 SEO、不需要教程/博客落地页、不需要 SSG 架构。

### 9.2 实施方案

**纯 index.html 改动，零架构风险，当天可完成：**

1. **静态 SEO 文案**：在 `index.html` 的 `<body>` 中写入一段静态可见的产品介绍文案。React 挂载后覆盖它，但爬虫和社交抓取器能直接读取。

2. **OG 标签**（`<head>` 中补全）：
   - `og:title` — 产品名称 + 一句话定位
   - `og:description` — 产品功能简述
   - `og:image` — 品牌预览图（1200×630px）
   - `og:url` — shufuri.com（域名注册完成后替换）
   - `twitter:card` — summary_large_image

3. **Meta 标签**：
   - `<title>` — 精准包含核心关键词
   - `<meta name="description">` — 搜索结果摘要文案（内容策略师撰写）

4. **sitemap.xml + robots.txt**：允许抓取首页，屏蔽 `/api/` 路径。

### 9.3 为什么不需要 SSG

| 顾虑 | 实际情况 |
|------|---------|
| "爬虫只看到空壳" | Googlebot 有 headless Chromium，能执行 JS 渲染 CSR 页面并索引渲染后内容。百度 JS 能力弱，但首页静态文案已覆盖 |
| "社交分享卡片读不到内容" | OG 标签写在 index.html 的 `<head>` 中，社交平台（微信/小红书/QQ）直接读取，不执行 JS |
| "需要多个页面被收录" | JULIA 确认只需首页被收录。FAQ、关于页作为 CSR 页面存在，不追求 SEO 收录 |

### 9.4 何时重新评估

以下任一条件触发时，再评估 SSG（vite-ssg 或 Next.js 迁移）：
- 需要多页 SEO（教程、博客、独立歌词落地页）
- 百度收录成为瓶颈且静态文案不足以覆盖

### 10.4 端到端主流程

### 4.1 标准路径（外部 AI 管线）

1. 首页填写歌名/歌手，选择语言波轮（JAP/KOR/ENG/中文）
2. 「一键生成指令」→ 口令写入剪贴板 → 跳转外部 AI App
3. 用户在豆包等粘贴口令，AI 返回记录流（`@0 … @9`）
4. 回到 SHUFURI：自动剪贴板弹窗 或 手动「粘贴并排版」
5. 确认 → `compileDocument` → **edit** 模式
6. 可选墨微调 → **export** → 保存歌词本 / 导出 PDF·PNG

| 入口 | 触发条件 | 行为 |

| QQ/网易云分享链接 | 剪贴板含分享 URL | 解析歌名/歌手预填；推断 jp/ko |

### 10.11 学习卡

从记录流 `V|` / `G|` 区段提取词汇与语法点，存入独立 IndexedDB `japanese-kana-app-study-cards`，在首页抽屉浏览、导出 Anki TSV。

### 11.1 触发时机

| 时机 | 行为 |
|------|------|
| 粘贴并排版 | 从 raw 提取词卡，绑定当前 `bundleId`（未保存时为 `session-*`） |
| 保存歌词本 | `session-*` 迁移为项目 `id`，再同步词卡 |
| 从歌词本打开 | 以项目 `id` 为 `bundleId` 重新同步 |

受设置「附词解与语法」控制；raw 无 `V|`/`G|` 行时不写入。

### 11.2 全局去重（重点）

**目标**：同一学习语种下，同一词条只保留一张词卡；重复导入同一首歌或不同歌含相同词时，词卡库不增殖。

| 规则 | 说明 |
|------|------|
| 去重键 `dedupeKey` | `` `${lang}\|${kind}\|${canonicalTerm}` `` |
| `lang` | 排版管线语言：`jp` / `ko` / `en` / `zh` |
| `kind` | `vocab` 与 `grammar` **分开**去重（同形可同时各一张） |
| `canonicalTerm` — 词汇 | `V\|` 第 1 列 `sourceRaw`：`trim` → jp/zh 走 `normalizeRubyMarkupText` → Unicode NFC |
| `canonicalTerm` — 语法 | 语法标题**括号前原形**（如 `は（助词）` → `は`），再同样规范化 |
| 命中已有键 | **保留库中已有卡**（`id` / `createdAt` 不变），跳过新 draft |
| 同批写入 | 同一 `dedupeKey` 仅写第一张，其余 skip |
| 按 bundle 替换 | 同步时先删除该 `bundleId` 下旧卡，再对剩余库做全局去重后插入 |

**刻意不做**：按歌名/项目隔离去重（两首歌同词仍合并为一张）；多来源 `sourceLabel` 拼接（v2 可选）。

### 11.3 存储与迁移

- Object store：`study-cards`；字段含 `dedupeKey`
- 索引：`bundleId`、`createdAt`、`dedupeKey`（**unique**）
- DB 版本升级（v1→v2）：为存量卡回填 `dedupeKey`；同键多条时保留 **`createdAt` 最早** 的一条，其余删除

### 11.4 导出

- Anki TSV：`buildAnkiImportTsv`；去重后同语种同词不会重复出现在导出列表

## 附录 A：排版引擎锁定清单

> 来源：AGENTS.md 第七节，修改排版引擎前必须遵守的约束

| # | 约束 | 风险 |
|---|------|------|
| 1 | `createPosterMeasurer` 中 wrapper.width/height 必须 = canvasW/canvasH | 否则 `width:100%` / `max-width:100%` 计算错误 |
| 2 | `createPosterMeasurer` 中 shell 必须 `Object.assign(..., buildFuriganaPosterRootStyle(profile))` | 缺少 `display:flex` 等导致测量和渲染不一致 |
| 3 | shell 不能是 `position: fixed`（测量容器 + 导出挂载均适用） | 内部 `max-width:100%` 按视口宽度算，高度低估；html2canvas 栅格化空白 |
| 4 | `body.style.maxHeight` 计算公式不能改 | `shellInnerH - titleH - titleMB - SAFETY_MARGIN_PX` |
| 5 | `.fv-body-h` 必须 `flex: 1 1 auto; min-height: 0; overflow: hidden` | flex 收缩 + 溢出裁剪 |
| 6 | `.lyrics-group` 不能被拆分（`isCompleteLyricsGroup` 检查） | jp/zh 分离破坏歌词阅读 |
| 7 | `joinPageBlocks` 必须在全页范围内只保留一份区段标题 | 区段标题去重 |
| 8 | `SAFETY_MARGIN_PX` 和 `FIT_EPSILON_PX` 不要随意缩小 | 内容截断/溢出 |
| 9 | `getFuriganaCanvasInsets` 的 bottom 和 `getFuriganaBodyBottomPaddingPx` 要联动 | 正文底部空间 vs 页码空间 |
| 10 | 字体通过 `@font-face` 注入（`POSTER_JP_FONT_FACE_CSS`），修改字体必须同步更新测量容器与导出挂载 | 字体尺寸差异导致溢出误判 / 栅格化字体错位 |
| 11 | 导出挂载中禁止 clip-path / opacity:0 / visibility:hidden / z-index:-1；改用全屏白色 backdrop 遮罩 | html2canvas 栅格化空白 PDF 零字节、PNG 导出无反应 |
